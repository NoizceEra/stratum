# STRATUM

A persistent shared-world game. One finite world per map — 1,048,576 tiles, fixed forever.
Everyone builds in it. Nothing anyone places is ever lost.

Browser client, zero dependencies. `npm start` and you're playing.

---

## The idea

Most persistent-world games solve the content problem by resetting, and solve griefing with
moderators. STRATUM does neither, by splitting the world into two layers with two different rules:

| Layer | What it is | Rule |
|---|---|---|
| **Persistent** | Player-placed tiles | **Never resets.** What you place, you own. Nobody can overwrite it. Ever. |
| **Volatile** | Resource nodes + monsters | **Resets on timers.** Generated by the world, not authored by players, so resetting costs nobody anything. |

That split is the whole game design:

- **No moderation queue, no admins.** Ownership is absolute, enforced server-side. There is
  nothing to report and nobody to appeal to.
- **No content treadmill.** The provender resets itself; the landmarks accumulate.
- **A real endgame.** The world is finite and never expands. Land is the only scarce resource,
  and there is a fixed amount of it. The HUD shows the running total: `% of world claimed`.

**The wilderness is a commons.** Anyone may build on unclaimed terrain — that is where all the
contest lives. Once you claim a tile, only you can alter it, and you can always give it back.

## Run it

```
npm start
```

Then open <http://127.0.0.1:8090>. (Or double-click `START.bat`, which starts the server and
opens the browser for you.)

To play **with someone else**: they open `http://<your-lan-ip>:8090` from the same network.
For anyone outside it, the server needs to be reachable — a static host will not work, because
a persistent world needs a long-lived process and a database. Railway/Fly/a VPS will.

### Controls

| | |
|---|---|
| `WASD` / arrows | walk |
| **LMB** | context action — strike a beast, else harvest a node, else build |
| `RMB` | give land back to the commons |
| `1`–`0` | choose material |
| wheel | cycle material |
| `M` | world map |
| `T` | travel between maps |
| `+` / `-` | zoom |

### Maps

| # | Name | Character |
|---|---|---|
| 0 | THE FIRST ACRE | Verdant and open. Where everyone starts. |
| 1 | ASHEN HOLLOW | Broken rock, shallow soil, heavy ore. Almost nothing grows — bring your own timber. |
| 2 | THE SUNKEN SHELF | Islands and shallows. Land is scarce here, and contested. |

Land does **not** leak between maps. The same coordinates on two maps are two different tiles.

## Share it

**This cannot be hosted on Vercel, Netlify, or any static host.** Two hard blockers:

- Serverless functions are ephemeral and cannot hold the long-lived WebSocket every player
  needs. STRATUM is a stateful socket server, not a request/response app.
- There is no persistent disk, so `data/world.db` — the entire point of the game — has nothing
  to live on.

Three options that do work:

**1. Same network (instant).** Find your LAN IP (`ipconfig`) and open `http://<lan-ip>:8090` from
any device on the same wifi. No setup, no tunnel.

**2. Temporary public URL (instant, what `SHARE.bat` does).** Cloudflare quick tunnel, no account
needed:

```
npx -y cloudflared tunnel --url http://127.0.0.1:8090 --no-autoupdate
```

It prints an `https://<random>.trycloudflare.com` URL that works from anywhere, including mobile
(HTTPS, so `wss://` upgrades work). Caveats: the URL is **random and changes every restart**, it
only lives while your machine is on and cloudflared is running, and anyone with the URL can join
and claim unclaimed land.

**3. Real hosting (permanent).** Railway, Fly.io, or any VPS. What a persistent world needs:
a long-lived Node process, a persistent volume for `data/`, and a host that allows WebSocket
upgrades. Railway and Fly both do; a static host never will.

### Mobile

The client is fully playable on a phone — it detects a touch device and swaps the keyboard for
on-screen controls:

- **Virtual joystick** (bottom left) — analog: a partial push walks slowly
- **Tap the world** — strike / harvest / build, whatever is under your finger
- **Hold the world** (~half a second) — give land back, the same as right-click
- **Buttons** (right edge) — map, travel, zoom

## Test it

```
npm test
```

Three phases, all against real servers with real WebSocket clients — no mocks:

- **A — protocol suite** (35 assertions): ownership is absolute, reach and bounds enforced,
  maps are isolated, nodes harvest → deplete → reset, monsters fight → die → respawn.
- **B — restart setup**: claims land on two maps and depletes a node with its *real* 90s timer.
- **C — restart verify**: reboots against the same database and proves the land is intact
  while the node is still regrowing.

Phase A scales the respawn clocks down (`STRATUM_RESPAWN_SCALE`) so the reset loop can be
observed in seconds instead of minutes. Phases B and C use real timers.

`node probe.js` is a small diagnostic that walks a character to a node and reports exactly what
the server says — useful when a test fails and you need to know which side is wrong.

## Layout

```
server.js              transport, sessions, land ownership, players  (node:http + node:sqlite + hand-rolled RFC 6455)
world.js               the VOLATILE layer: nodes, monsters, respawn timers
public/terrain.js      deterministic world generation — shared verbatim by client and server
public/game.js         client: renderer, input, netcode
public/index.html      shell, HUD, gate, travel panel
test.js                protocol suite (phase A)
test-restart.js        restart persistence (phases B/C)
run-tests.js           orchestrates the phases, spawning each server as a child
data/world.db          the world. Delete it to reset everything.
```

### Two things worth knowing about the design

**The base terrain is never stored.** It is a pure function of `(map, x, y)` in `public/terrain.js`,
which is the *same file* the server runs. The client regenerates terrain locally for free; only
player edits travel over the wire as sparse deltas. The two can never disagree about what the
world looks like, because there is only one implementation.

**The server is authoritative and does not trust the client.** Every placement is re-validated
against reach, bounds, ownership, material and energy. Movement is rate-limited. Respawn timers
are the server's.

## Commerce (Robinhood Chain)

Harvesting, crafting, and kills award **in-game gold** plus pending **STRM** token units.
The token contract is configured in `src/token-config.js` (Robinhood Chain `4663`).

Placeholder CA (replace soon):

Override without code changes:

```
STRATUM_TOKEN_ADDRESS=0x…
STRATUM_CHAIN_ID=4663
STRATUM_RPC_URL=https://rpc.mainnet.chain.robinhood.com
STRATUM_TOKEN_SYMBOL=STRM
```

Connect a wallet in the HUD to switch to Robinhood Chain and read on-chain `balanceOf`.
Pending STRM is a server ledger — on-chain claim/mint is a follow-up once the official
token is live.

## Status

Playable and tested. Honest gaps:

- **Token claim not live yet** — pending STRM accrues in SQLite; no mint/transfer until the
  official contract + treasury/minter path exists.
- **Not deployed.** It runs locally. Hosting needs a long-lived process (Railway/Fly/VPS) plus the
  static client — not a static host alone.
- **Anti-cheat is basic** — movement rate-limiting and server-side validation, no persistence of
  suspicion.

### Reset everything

```
rm -rf data/
```

That is the only way to reset. There is no in-game wipe, by design.
